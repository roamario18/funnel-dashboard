# Дашборд воронки продаж

Приложение показывает аналитику сделок CRM текущего пользователя внутри Битрикс24.

**Портал:** `https://bs18.bitrix24.ru` → левое меню **«Воронка продаж»**.  
**Контейнер (только из меню):** [https://app-7a4dbac2cc1e.vibecode.bitrix24.tech](https://app-7a4dbac2cc1e.vibecode.bitrix24.tech)  
**Исходники:** [https://github.com/roamario18/funnel-dashboard](https://github.com/roamario18/funnel-dashboard)

Прямая ссылка Black Hole даёт 401 (`OWNER_ONLY`) — открывать из меню, не по URL `app-…`.

## Сценарии

- KPI наверху — три числа за период: сумма открытых сделок, число выигранных, средний чек. Считаются через `POST /v1/deals/aggregate` по одной валюте (`filter.currency`, `groupBy: stageId`), суммы пересчитываются по курсу CRM и складываются в рубли.
- Сводка по стадиям — те же агрегаты, не таблица сделок.
- Выбор воронки CRM (основная и дополнительные).
- Последние 20 сделок (`POST /v1/deals/search`, `limit: 20`): название, сумма в валюте сделки, стадия, ответственный. Это не KPI.
- Фильтр по дате создания: 7 дней / 30 дней / все время. Сделки за сегодня входят в 7 и 30 дней.
- Открытие из левого меню (placement отдаёт `code` без `state`) ставит сессию само, без ошибки `invalid_state`.

Работает от лица вошедшего сотрудника (`vibe_app_` + сессия). Ключ и вызовы Vibe API только на сервере (BFF). Секреты в `.env`, не в git.

## Скоупы

Боевой ключ приложения (`vibe_app_`), режим **`READONLY`**:

| Скоуп | Зачем |
| --- | --- |
| `crm` | Сделки, стадии, поиск и `POST /v1/deals/aggregate` |
| `user` | ФИО ответственного |
| `placement` | Пункт левого меню портала |

`vibe:infra` на ключе нет. Платформа сама оставляет на `vibe_app_` скоупы `vibe:ai` и `vibe:search` (модели и веб-поиск); в карточке они не снимаются. Дашборд их не вызывает; в `READONLY` запись в эти разделы закрыта. Актуальный срез без секрета — [docs/me.json](docs/me.json).

## Ограничения

- Доступ: пункт левого меню виден сотрудникам портала `bs18.bitrix24.ru`. Учётка для проверки передаётся в переписке по тикету.
- Суммы открытых, средний чек и стадии считаются в рублях: список валют из `GET /v1/currencies` **с курсом** (базовая или ненулевой `amount`), по каждой — отдельный `POST /v1/deals/aggregate` (`filter.currency`, `groupBy: stageId`), затем пересчёт по курсу справочника. Курс портала, не биржи. В таблице последних сделок сумма остаётся в валюте сделки. Если валют несколько — предупреждение с использованным курсом; если курса в CRM нет — сумма входит в KPI без пересчёта, тоже с предупреждением.
- Если агрегат по всем валютам не прошёл — `/api/dashboard` отдаёт ошибку (`sendApiError`), а не нули KPI. Частичный отказ CRM — предупреждение с причиной. Хвост очереди, который не успели начать за ~18 с, и коды без курса (например устаревший BYR) предупреждением не показываются, если живые валюты посчитались. Подпись «Нет сделок за выбранный период» только для пустой выборки.
- Агрегация ограничена 5000 сделками на валюту; при обрезке показывается предупреждение.
- Первый заход ждёт CRM. Справочники воронок, стадий и курсов кэшируются в памяти процесса **45 секунд**. KPI — валюты справочника с курсом, агрегаты **по очереди** (сначала RUB), один вызов до 20 с, на пачку ~18 с. На 429 у справочников — одна повторная попытка по `Retry-After` (не дольше 2 с).
- Сессия `vibe_app_` живёт 24 часа, без автопродления.
- Пустая выборка — empty-state, не ошибка.
- Поштучный запрос пользователей — только при сбое сети / 5xx; на 401/403 в таблице остаётся `ID`.

## Как проверить

1. Левое меню **«Воронка продаж»** — должен открыться дашборд, не `invalid_state`.
2. Фильтр 7 / 30 дней — сделки, созданные сегодня, в списке; KPI (открытые / выигранные / средний чек) и стадии пересчитываются. Второй клик по периоду обычно быстрее первого: справочники ещё в кэше.
3. Смешение валют — KPI и стадии в ₽ с копейками, в таблице исходная валюта, над таблицей предупреждение с курсом CRM.
4. Пустой период — empty-state, не ошибка.
5. Сотрудник без CRM должен увидеть понятную ошибку прав, а не нули KPI и не «Нет сделок за выбранный период».

## 1. Ключ в режиме READONLY и вывод `/v1/me`

**Цитата проверяющего.** Перевести `vibe_app_` в `READONLY` после разовой привязки меню и приложить `GET /v1/me` без самого ключа: `accessMode: "READONLY"` и фактические скоупы. (существ. 1; закрывает средн. 6 в части подтверждения ключа.)

**Как воспроизводилось.** `GET /v1/me` с боевым ключом давал `accessMode: "READWRITE"`. Файл [docs/me.json](me.json) тоже `READWRITE`.

**Как проверить сейчас.**

1. Кабинет Вайбкод → ключ авторизации приложения дашборда (суффикс `4765`).
2. Блок «Режим доступа» → «Только чтение».
3. Повторить `GET https://vibecode.bitrix24.tech/v1/me` с заголовком `X-Api-Key` (ключ не логировать).
4. Ожидание проверяющего: `"accessMode": "READONLY"`.

**Срез после перевода в чтение:** `"accessMode": "READONLY"`. Файл [docs/me.json](me.json) обновлён (без самого ключа). Повторный деплой этим ключом недоступен (`WRITE_BLOCKED_READONLY_KEY`) — так и должно быть.

**Комментарий.** Режим держали `READWRITE`, пока создавали сервер и биндили меню. После проверки дашборда из меню переключили на «Только чтение».

## 2. Убрать `vibe:infra` с боевого ключа

**Цитата проверяющего.** Деплоить личным `vibe_api_` либо выпустить приложение со скоупами только `crm`, `user`, `placement`. (средн. 2)

**Как воспроизводилось.** У ключа приложения в скоупах были платформенные `vibe:infra`, `vibe:ai`, `vibe:search`, `vibe:storage`.

**Как проверить сейчас.** Тот же `GET /v1/me` → массив `scopes`. Нужно ровно: `crm`, `user`, `placement`.

**Срез после правки приложения:** у парного ключа `4765` — `crm`, `user`, `placement`, `entity`. Платформенных `vibe:*` нет. У записи приложения в API — ровно `crm`, `user`, `placement`.

**Почему в кабинете «не снимаются» галочки.** Экран, где `placement` / `entity` «недоступно для персонального ключа — нужно OAuth-приложение», относится к **личному** `vibe_api_`, не к ключу дашборда. `vibe:ai` и `vibe:search` на форме личного ключа платформа снова проставляет при сохранении — это предвыбор вкладки «Вайбкод».

`placement` на OAuth-приложении снимать нельзя: без него пропадёт пункт левого меню. `entity` попал в парный ключ в момент выпуска (тогда прав было много); скоупы Битрикс24 у уже выпущенного `vibe_app_` не сужаются без перевыпуска. Перевыпуск сейчас не делаем: ключ в env контейнера и режим уже `READONLY`.

**Комментарий для проверяющего.** `vibe:infra` снят. `vibe:ai` / `vibe:search` с парного ключа сняты через `PATCH` приложения. Остался `entity` как след широкого выпуска; дашборд хранилище `entity` не вызывает. `placement` нужен для встройки.

## 3. Ветка одноразового `code` → `invalid_state`

**Цитата проверяющего.** Починить или удалить приём кода в `server.js:46-52` — сейчас всегда `invalid_state`. (средн. 3)

**Как воспроизводилось (до правки).**

1. Открыть дашборд из левого меню (placement отдаёт `/?code=…` **без** `state`).
2. Старый код редиректил это на `/auth/callback`, где обязателен `state` из cookie логина.
3. Итог: `invalid_state`, сессия не ставилась.

**Как проверить сейчас.**

1. Выйти из приложения / сбросить cookie `vibe_session` (или открыть меню в режиме инкогнито, затем зайти на портал).
2. Левое меню → дашборд. В адресе iframe может мелькнуть `code=` без `state`.
3. Экран дашборда со сделками, **не** ошибка `invalid_state`.
4. В коде: `исходники/source/server.js`, обработчик `GET /` — ветка `if (code && !state)` меняет код через `POST /v1/oauth/token` с `redirect_uri` = origin приложения, ставит cookie, редирект на `/`.

**Комментарий.** Редирект на `/auth/callback` оставили только если есть **и** `code`, **и** `state` (ручной «Войти через Битрикс24»). Placement-код без `state` больше туда не отправляется.

## 5. Поштучный фолбэк пользователей на 401/403

**Цитата проверяющего.** Не вызывать фолбэк `GET /users/:id` на 401/403, только сеть и 5xx. (средн. 5)

**Как воспроизводилось (до правки).** При ошибке `users/search` код всегда ходил в `/v1/users/:id` по каждому ответственному, в том числе при отказе в правах.

**Как проверить сейчас (по коду, без ломки прав).**

1. Открыть `исходники/source/lib/dashboard.js`, функция `loadUsers`.
2. В `catch`: `transient = status === 0 || status >= 500`.
3. Если не transient (401/403/4xx) — в таблице `ID N`, без второго запроса.
4. Поштучный `GET /users/:id` — только при сбое сети / 5xx.

**На экране:** сотрудник с CRM видит ФИО; при отказе `user` — `ID`, не каскад запросов.

## А. Фильтр 7 / 30 дней прятал сегодняшние сделки

**Не из письма проверяющего** — поймали на тестовой сделке в $.

**Как воспроизводилось.** Сделка «тест валюты», `createdAt` сегодня ~22:12 МСК. Фильтр **«Все»** — видна. **«7 дней»** и **«30 дней»** — нет (на 30 днях оставались только августовские). Воронка была верная.

**Почему.** Vibe/Bitrix обрезает `$lte: сейчас` по `createdAt` до **полуночи UTC этой даты**. Всё созданное 1 сентября после 03:00 МСК для API «уже после конца дня».

**Как проверить сейчас.** Фильтр **7 дней** → сделка за сегодня в списке. В коде: `исходники/source/lib/period.js` — верхняя граница = начало **следующих** суток UTC (`utcTomorrowIso`), не `new Date()`.
